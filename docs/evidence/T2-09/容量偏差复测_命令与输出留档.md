## 2. 探活排障实录（新坑，已回填 vm-ops 技能坑⑤与《环境基线》§3）

首轮探活循环 `guestcontrol run -- cmd /c echo alive` 连续超时，错误形如：

```
VBoxManage.exe: error: Details: code VBOX_E_IPRT_ERROR (0x80bb0005), component GuestProcessWrap ...
VBoxManage.exe: error: Context: "WaitForArray(...aWaitStartFlags..., 30 * 1000, &enmWaitResult)" ...
```

排查走弯路的过程如实留档：
1. 首轮循环用 `2>/dev/null` 吞掉了 stderr——**真实报错全程不可见**，误导排障方向（教训①）；
2. 误判一"账号锁定"：早期口令提取模式写错（登记物无 `net user` 行，回退模式匹配到 `/t` len=2），
   实际是**口令为空/错误 + 参数被篡改**叠加；`controlvm screenshotpng` 截图见 acc-22h2 桌面已正常
   autologon（锁定假设排除）、acc-24h2 黑屏（headless 显示器断电，属正常）；
3. 误判二"GA/会话损坏"： graceful 重启双机（ACPI 关机双双超时 90s+ 按预案强断）后仍超时；
4. **根因**：漏置 `MSYS_NO_PATHCONV=1`（vm-ops 坑①）。MSYS 把 guest 命令参数（`/c` 等）做路径转换，
   损坏后的命令使 `run` **不表现为立即报错，而是挂在进程启动回执等待（30s 超时）**——与
   "GA 未就绪/账号锁定"症状同形，极易误诊。另外文件通道类操作（mkdir/copyto/copyfrom）不含
   `/` 开头参数，不受影响，故 `mkdir` 成功而 `run` 失败的现象进一步掩盖根因；
5. 修复后一次通过（探活勿吞 stderr + MSYS_NO_PATHCONV=1 + 完整路径 exe 为最稳形态）：

```
$ export MSYS_NO_PATHCONV=1
$ VBoxManage guestcontrol L1-acc-22h2 run --username qa --password ****** \
    --wait-stdout --wait-stderr -- 'C:\Windows\System32\cmd.exe' '/c' 'echo alive'
alive
```

**副作用披露**：排障期间对双机各执行了一次无谓重启（ACPI 关机超时 → 强制 poweroff，差分盘无关键
未落盘数据，快照/镜像未动）；`controlvm screenshotpng` 在 7.2.22 非顶级命令，正确形态为
`VBoxManage controlvm <vm> screenshotpng <file>`。今日两次收尾关机（§7）ACPI 亦超时走预案
（首轮记录仅 24H2 超时，22H2 本日两轮均超时——疑似桌面 autostart 窗口阻碍，未深查）。

## 5. 宿主校准记录（方法学闸门：校准不通过不得作为 VM 基准来源）

参考脚本先在宿主对 `tools/baseline.json` 的 Explorer 登记值（2026-10-31 注册）校准：

| 目录 | Explorer 登记 | v1 GCFW 求和 | v1 偏差 | v2 纯句柄 | v2 偏差 |
| --- | --- | --- | --- | --- | --- |
| Local\Programs | 2,490,138,624 | 2,446,769,871 | **1.742% ✗** | 2,492,484,472 | **0.094% ✓** |
| Roaming\Tencent | 9,745,108,992 | 9,744,661,232 | 0.005% | 9,794,711,160 | 0.509%（活跃目录漂移，同扫描器当日 0.345~0.394% 漂移量级） |
| Package Cache | 412,831,744 | 412,735,888 | 0.023% | 412,832,472 | 0.000% |

- **v1（GetCompressedFileSizeW）废弃根因（最小实验实证，宿主 C: 卷簇 4096B）**：GCFW 对普通
  （非压缩/稀疏）文件返回**逻辑大小**而非占用空间——

  | 逻辑大小 | 100 | 601 | 1024 | 2000 | 4095 | 4096 | 5000 |
  | --- | --- | --- | --- | --- | --- | --- | --- |
  | GCFW | 100 | 601 | 1024 | 2000 | 4095 | 4096 | 5000 |
  | 扫描器句柄实查 | 104 | 608 | 4096 | 4096 | 4096 | 4096 | 8192 |

  （601B 文件恰处 DR-004"驻留不稳定窗口"，实查 608B 属驻留边缘态；700B+ 均非驻留。）小文件密集树
  （如 Programs）逐文件簇级空隙累积 → v1 校准 1.742% 超阈；Tencent/Package Cache 恰以大文件/压缩
  稀疏为主而巧合吻合。v1 判定：不得作为基准来源，JSON 留档备查（`*_v1_GCFW_废弃.json`）。
- **v2（纯句柄）采纳依据**：逐文件 `FILE_STANDARD_INFO.AllocationSize` 即文件系统自报分配量，
  是 DR-004 ②' 梯度夹具（混合 vs 纯句柄 <0.1%）与扫描器 ①③ 段同一外部真值锚点，实现路径与扫描器
  相互独立；静态目录校准 0.094%/0.000%，通过。文件、口径对齐声明与兼容性说明见
  `容量偏差复测_基准重建脚本.ps1` 头注（PS 5.1/GBK 宿主要求纯 ASCII）。
- 附带发现：`tools/check_size_deviation.py` docstring"零第三方依赖下无可靠程序化取数途径"的论断
  限于 Shell COM 口径；句柄实查（kernel32）可程序化取得与扫描器/资源管理器一致的分配量——该论断
  不必修改（其语境是"不采用 Shell COM"的决策记录），此处仅作口径备注。

## 8. 已知限制

1. `C:\ProgramData\Package Cache` 双机不存在——VM 未装触发 bundle 缓存的负载；宿主基准三目录中的
   该目录在 VM 侧以 MISSING 披露，不构成缺口（偏差对比覆盖 4 个真实存在目录）。
2. VM 侧 Roaming\Tencent 仅 2 文件（249,856B）——VM 上微信/QQ NT 大数据体在别处（Local 等），
   本目录是宿主同名的形式对齐，样本意义有限；kingsoft（2.7GB/12.6k 文件）承担大目录口径压力。
3. 基准重建与本程序扫描非原子：同机同目录两测相隔秒级，活跃目录（kingsoft）漂移贡献 ~0.1% 偏差
   （宿主 Tencent 同现象），不影响 <1% 判定。
4. 参考脚本排除目录自身 MFT/索引开销（与扫描器"仅文件计量"对齐）；资源管理器登记值与扫描器的
   0.0x% 一致性间接证实该口径与 Explorer 相容，未单测目录开销项。
5. 参考脚本 PS 5.1 无长路径（>260 字符）支持：VM 侧 fail=0（无受影响路径）；如未来目录含超长路径，
   两侧 skip 语义不对称需注意（本程序有 `\\?\` 长路径支持）。
