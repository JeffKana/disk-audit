结论速览
  1. 性能不是问题，而且余量极大。全盘 C: 1,371,543 项 15.23 秒、峰值内存 25.5MB。原方案里"MFT 直读"这个高风险备选可以直接删除——用不上。
  2. 8 线程是最优，16 线程没有收益（全盘 15.23s vs 15.34s；AppData 4.94s vs 4.79s）。线程数按 8 定，少一半并发不损失速度。
  3. 发现缺陷①（正确性，比性能重要）：并行切分（frontier）只统计了切分点以下，导致全盘体积少算 14.76GB（156.66GB → 141.90GB）——漏的是 pagefile.sys/hiberfil.sys 这类根级大文件。必须在切分层显式补算，否则报告的数字是错的。
  4. 发现缺陷②（打包，会直接崩）：本机 managed Python 3.13.12 没有 Tcl/Tk，用它打包出的产物运行即 ModuleNotFoundError: No module named 'tkinter'。换用系统 Python 3.13.5（Tcl/Tk 8.6）后全部正常。构建环境必须固定。
  5. 另外记录一个死锁坑：线程池内嵌套 submit + result() 会死锁（首版实测 5 分钟零进度、CPU 仅 9 秒）。已改为"浅层切分 + 叶级单线程递归"，这条要写进代码规范。

POC-1　枚举性能：全盘/目录扫描到底多快

方法：os.scandir 逐项读元数据（不读文件内容、不落盘），跳过 reparse point 防 Junction 循环；对比单线程与 frontier 并行（先 BFS 切出前沿目录，再对每个前沿目录单线程递归，全程无嵌套 submit）。

缺陷①：并行切分漏算"切分点之上"的文件（体积少算 14.76GB）
frontier 方案只统计前沿目录及其子树，前沿之上的层级（C:\ 根目录、C:\Users\xxx 等）里的文件被完全跳过。而根目录恰恰放着 pagefile.sys、hiberfil.sys、swapfile.sys 这类单文件即 GB 级的系统文件——差值 14.76GB 就是它们。
修复：切分阶段必须同时统计每一层"未被继续下钻的目录中的文件"，并计入总数。这条不是优化项，是正确性缺陷：如果报告里"全盘占用"比资源管理器少 15GB，用户第一反应是"这工具连容量都算不准"，信任直接归零。
顺带：denied=472（0.03%）必须在报告里以"未扫描 472 项"披露，不能静默吞掉——对应方案风险 R8。
判定：通过，且远超预期。AppData 4.8s（目标 8s）、全盘 15.2s（目标 120s，余量 8 倍）。
对方案的影响：① 删除"直读 NTFS MFT"备选（原列为 POC 后的风险分支，现已无必要）；② 线程数定为 8；③ 全盘扫描目标可从 120s 收紧到 30s，把余量留给 HDD 和老机器。

缺陷②：构建解释器缺 Tcl/Tk，产物启动即崩
第一次打包（managed Python 3.13.12）产物只有 52 个文件、19.8MB，看起来更"轻"，但运行自检返回 tkinter: FAIL: ModuleNotFoundError("No module named 'tkinter'")——它在用户机器上会在弹出窗口前就崩掉。原因是该解释器未安装 Tcl/Tk，PyInstaller 分析不到就静默跳过（构建日志无报错）。
换用系统 Python 3.13.5（Tcl/Tk 8.6）后：982 文件 / 24.9MB，Tkinter 正常，注册表/Appx/枚举全部正常。代价只是 +5.1MB 与 +930 个 Tcl/Tk 运行文件。
修复（写进方案）：① 构建环境固定为带 Tcl/Tk 的 CPython，并在 CI 里加一条 python -c "import tkinter" 的前置断言；② 发布前必须跑 --selftest 并把 tkinter 检查作为通过条件。
顺带一个诚实说明：剥离 PATH 后第一次自检里 Appx 也报 FileNotFoundError，我一度以为是缺陷。复查发现是我测试手法的问题——把 PATH 裁到只剩 system32，而 powershell.exe 在 System32\WindowsPowerShell\v1.0\ 下，自然找不到。恢复正常 PATH 后返回 199 个包。这不是产品缺陷，但暴露一个真实依赖：产品对 powershell.exe 的依赖必须显式处理（绝对路径调用 + 失败降级），否则在安全加固过的机器上会静默丢掉整个 UWP 判定分支。

方案变更清单（因 POC 结果而改）

编号变更类型内容
C1删减删除"直读 NTFS MFT"备选路线。原方案把它留在 POC 后作为风险分支；实测全盘 15.2s 已达标 8 倍余量，MFT 解析的复杂度不再值得承担
C2确定参数枚举并行度定为 8 线程（16 线程无收益）；采用"浅层 frontier 切分 + 叶级单线程递归"，禁止线程池内嵌套 submit
C3修缺陷切分统计口径修正：必须补算前沿以上层级的文件，否则全盘体积少算 14.76GB。列入 M1 验收项（"报告总容量与资源管理器偏差 <1%"）
C4修缺陷构建环境固定：必须使用带 Tcl/Tk 的 CPython（本机 D:\develop\environment\python 3.13.5 合格；managed 3.13.12 不合格）。CI 增加 import tkinter 断言 + 发布前 --selftest 门禁
C5新增约束PowerShell 调用改为绝对路径（%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe）+ 失败降级；避免加固环境静默丢失 UWP 判定分支
C6新增披露报告中新增"未扫描 / 跳过"统计（本机全盘 472 项权限拒绝，0.03%），不得静默吞掉
C7确认UI 形态（启动器 + 静态 HTML 报告）经实测验证可行：5000 行 613ms、筛选 52ms，无需引入任何前端框架
