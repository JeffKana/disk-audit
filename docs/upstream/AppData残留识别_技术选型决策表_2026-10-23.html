一页结论
  1. 先过两道硬门槛，9 个方案只剩 3 个。门槛①"License 允许商用二开"（D8≥4）、门槛②"必须解决存量事后识别"（D1≥4）——同时通过的只有 S1 BCU 直接使用、S6 自研只读分析器、S7 BCU 源码二开。其余方案不是不好，是不满足本项目的硬约束。
  2. 两套权重下 S1 都排第一（场景A 4.37 / 场景B 4.25）。这个结果本身是结论："用现成" 在当前证据下优于 "自建"，因为 BCU 罕见地同时满足"能力最全 + Apache 2.0 可商用"。
  3. 但 S1 是"工具"不是"资产"。若目标是产品化引擎，S1 只能做能力基线与交叉验证基准，不能作为产品内核；需要自有引擎时，起点是 S6（1~2 周 MVP，89% 自动归属已被实测证明）。
  4. S7 是"加速器"不是"起点"。Apache 2.0 允许二开，但 C#/.NET 8 中大型代码库的学习成本（D10=2）与分叉同步成本，使其不适合作为第一阶段投入。
  5. 明确不建议：S8 云规则库（合规 D6=1 且不解本项目核心命题）、S4 Total Uninstall（只管未来，对 319 项存量零效力）。

二、决策逻辑：先筛硬约束，再比加权分

六、结论：推荐 / 备选 / 不建议

推荐方案

定位方案结论与理由
推荐 1
立即执行		 S1 BCUninstaller 直接使用
场景A 4.37（第1）/ 场景B 4.25（第1）		 先清存量，别先写代码。它是唯一同时满足"孤儿检测 + 卸载后残留 + 置信度评级 + Apache 2.0"的方案，成本/周期双 5。用法：便携版全盘扫描 → 与报告 CSV 交叉验证 → 只按高置信 16 项人工确认后经回收站删除；同时把"卸载后残留扫描"设为默认习惯，从源头止血。预期释放 5~8GB（不动开发缓存）。
推荐 2
若要做引擎		 S6 自研只读分析器（Python）
场景A 3.73（第2）/ 场景B 3.86（第2）		 它是唯一能变成产品资产的候选。理由不是分数，是结构：S1/S7 拿到的是"别人的判定逻辑"，S6 拿到的是"自己的知识库 + 置信度模型 + 证据链"。MVP 单人 1~2 周、原型已验证 89% 自动归属，风险在可控区间。前提是死守三条原则：永不自动删除、每条判定出示证据链、删除只走回收站。
组合结论（这是真正的建议）：不是"二选一"，而是时间上串行、职责上分离——
① 第 0~1 周：用 S1 解决 C 盘空间（它已经够用，自研替代不了这个即时价值）；
② 第 1~3 周：用 S6 把"判定引擎"跑成自有资产，知识库从本机 320 项长尾开始沉淀，S1 的扫描结果作为交叉验证基准集（两套结果不一致的条目，就是最值钱的误判样本）；
③ 产品化阶段（≥3 个月）：仅在需要重写 UI / 深度裁剪安装包 / 需要成熟卸载流程时，再评估 S7 是否值得 fork——不提前。

定位方案什么条件下才启用
备选 1 S7 BCU 源码二开（C#/.NET 8）
场景A 3.54（第3）/ 场景B 3.67（第3）		 触发条件（满足任一）：① 产品确定要商业化、需要成熟的多渠道卸载（Steam/Oculus/Chocolatey）与静默批量；② 自研 S6 的知识库工程化撞到天花板，需要参考现成置信度实现；③ 团队本身有 C#/.NET 能力，学习成本 D10 可从 2 升到 4。不做起点，只做加速器。注意 Apache 2.0 的署名与声明保留义务。
备选 2 S5 PowerShell 社区脚本
场景A 3.40 / 场景B 3.39		 作为参考实现与"只读审计"交互范本（Windows-Orphan-Cleanup-Audit 的"默认只读 + 删除需显式开关 + 二次确认"正是本项目要的形态），以及 UWP 比对的官方姿势（Get-MsixOrphanedAppData）。前提：先核实各仓库 LICENSE，无 License 的代码只能读思路、不能复制。

S2（Geek/HiBit）与 S3（Revo Pro）不进备选名单——它们的加权分（3.47 / 3.44）低于基线 S9（3.52），意味着"为它们投入的注意力"在本项目目标下不如把精力放在 S1/S6 上。它们只适合"临时手头一台机器、要立刻卸载某个软件并清残留"这种一次性场景，与"存量识别"是两条路线。

不建议方案

方案名称不建议的核心原因
S8云规则库（360/管家式）两处硬伤。① 合规：需上传本机文件/进程/软件清单，属个人信息处理，D6=1 是全表最低；② 场景：报告明确指出该路线根本不做孤儿归属判定，即使建成也不解决"这 300 个目录属于谁"。再叠加重资产运营与 CleanMyPC 停运揭示的商业退潮，投入产出不成立。
S4Total Uninstall（快照 diff）技术精度最高，但对本项目无效。快照只覆盖"监控期间新装"的软件，本机 319 项是历史存量，快照一条都管不到（D1=2）。加上常驻 IO 开销与专有许可，这是"选错问题"而非"选错工具"。
S9不做（现状基线）唯一作用是证明"必须做"：C 盘剩 18.8GB 且会继续恶化，而现有工具只回答"哪里大"。列为基线对照，不列为选项。
S2Geek + HiBit 作为主方案能力边界在"卸载时"，对存量无解；且闭源 freeware 不可二开、不可审计，D8=1、D5=2。可作临时补充，不可作主线。
S3Revo Pro 作为主方案官方手册明言安全机制会故意漏报残留下——对本项目"追求高召回 + 分级置信"的目标是方向性冲突；且专有许可不可二开，存量场景仍需手动补扫。

八、切换与止损条件

触发条件应对

安全边界（不因选型改变）：本决策表及上游报告均为只读分析结论。Roaming\Microsoft\Protect（DPAPI 密钥）在任何方案下都不得删除——一旦删除，浏览器密码、证书、Wi-Fi 凭据将永久无法解密。XP 兼容 Junction（Application Data / History / Temporary Internet Files）同样硬黑名单。任何删除必须：核对证据 → 关闭应用 → 经回收站（可还原）→ 大规模操作前建还原点。
