二、三处必须先定夺的冲突

冲突①　面向普通用户发布（Q1=C）　vs　只出报告不删除（Q3=A）

问题："清理大师"这个名字 + 公开发布，用户预期是"一键清出 10GB"；但 v0.1 只给报告。这个落差会直接变成一星评价——而清理类工具的差评成本极高，因为用户会怀疑"是不是它删坏了我的电脑"。

对策（三选一，需你定）：

  • 1-A 改定位不改行为：对外叫"磁盘体检 / 残留诊断"，副标题写明"只诊断，不动手"。报告结尾给"下一步怎么做"的引导（打开系统存储感知、跳转应用卸载页、复制路径自行处理）。推荐
  • 1-B 保持"清理大师"名，只读作为 v0.1 的阶段性限制：风险是用户不会读版本说明，直接按"清理"预期打分。
  • 1-C 在报告里增加"可执行清单导出"：导出 .txt/.ps1（脚本只生成不执行，由用户自己审阅后运行）。这能显著提升"有用感"，但要额外做安全审查与免责说明。建议 v0.2

我的建议：v0.1 用 1-A；若内测反馈"看完不知道干嘛"占比 >40%，再上 1-C。→ 已确认（D3 改）：采纳 1-A，对外改为诊断类命名，副标题前置"只诊断不动手"。

冲突②　要安装包 + 自动更新（Q10=B）　vs　暂不签名（Q6）

问题：未签名的 .exe 安装包在 Win11 上会触发 SmartScreen"未知发布者"警告；而"清理/磁盘"类工具是杀软误报的高危品类——"扫描全盘 + 打包成 exe + 无签名"这个组合，被 Defender/国产杀软拦的概率不低。更严重的是自动更新：无签名的情况下，程序自动下载并执行新版本 = 一个现成的提权/投毒面，既危险又更容易被杀软判定为可疑行为。

对策（需你确认）：

环节v0.1 建议做法理由
分发主形态免安装 portable zip 为主，安装包为可选portable 不写注册表、不留痕迹，杀软与用户戒心都更低；也符合"只读"叙事
安装包Inno Setup 生成，不签名，README 明确写"会出现未知发布者提示，属预期"满足 Q10；把预期前置，减少"以为是病毒"的流失
自动更新降级为"版本提示"：启动时（可选关闭）请求 GitHub Releases 拿版本号，仅提示"有新版本"，不自动下载、不自动执行无签名时自动更新是安全债，见下方风险登记 R2
完整性每个 Release 附 SHA256SUMS；README 给出校验命令用户可自证下载未被篡改，部分替代签名的信任作用
误报处理发布前自查 VirusTotal；对主流杀软提误报申诉；README 提供"从源码构建"路径开源 + 可自构建是未签名产品的兜底信任

已确认（D1 同意）：自动更新降级为"仅版本提示，不自动下载执行"；主形态 portable zip + 可选安装包 + SHA256SUMS。代码签名不提前到 v0.1，等有用户基数后再评估（OV/EV 证书有年费，且仅 EV 具备即时 SmartScreen 信誉）。

冲突③　"只读"是限制，也是这个项目唯一稀缺的资产

市面上不缺能删的工具（BCU、Revo、HiBit 都能删）；缺的是"敢让你看清它凭什么这么判断"的工具。Q3=A 让"只读"成为可验证的产品事实，而不是营销话术。因此 v0.1 应把三件事做成硬约束，写进 README 与 UI：

  • 零写操作（除报告文件）：只向 %LOCALAPPDATA%\DiskCheck\ 写报告与缓存；不写注册表、不改文件属性、不动任何被扫对象。
  • 零联网（除你主动点的版本检查）：默认完全离线可运行；不收集任何统计。这条比"我们很安全"有力一百倍。
  • 证据链可见：每条判定都能展开看到"依据哪条规则/哪个注册表项/哪次进程快照"。

三、产品定位与 v0.1 范围

v0.1 做（In Scope）

  • 选择扫描范围：整盘（C:/D:…）或任意文件夹
  • AppData/ProgramData/用户目录的归属判定 + 残留分级（高/中/低置信）
  • 可回收空间分类：更新缓存、转储/临时、开发缓存（可勾选是否计入）
  • 生成离线 HTML 报告：概览 / 明细表 / 证据链 / 建议动作
  • 本地历史快照 + 两次扫描对比（月度体检场景）
  • 报告导出 CSV（供进阶用户二次分析）
  • 安装包 + portable 两种分发，Apache-2.0 开源

v0.1 明确不做（Out of Scope）

  • 任何删除/移动/重命名操作（Q3=A，永久不做于 v0.1）
  • 软件卸载功能（引导用户用系统或 BCU）
  • 安装监控 / 快照 diff（路线 A，成本高且与"存量"目标不符）
  • 服务端、账号、云规则库、匿名统计
  • Win10 / Windows Server / ARM64（Q4 明确 Win11）
  • 常驻托盘 / 实时监控（Q2=B 不需要）
  • 自动下载并安装更新（见冲突②）
  • 多用户/远程机器扫描（需加载他人 HKCU 蜂巢，v0.2 再评估）

MVP 需求条目（EARS 表述）

按项目规范用 EARS 句式写，每条可独立验收。Ubiquitous / Event-driven / Unwanted / State-driven 四类。

[U-1] The system shall 在未获得用户显式选择的扫描范围前，不读取任何文件系统路径。 [U-2] The system shall 以只读方式访问被扫描对象，除 %LOCALAPPDATA%\DiskCheck\ 外的任何位置不得产生写操作。 [E-1] When 用户选择扫描范围并确认，the system shall 在界面展示实时进度（已扫描条目数、当前路径、已用时），且进度刷新间隔不超过 500ms。 [E-2] When 扫描完成，the system shall 生成一份离线可打开的 HTML 报告，并为每条残留候选输出：路径、大小、置信度、判定来源、证据链、建议动作。 [E-3] When 本次扫描与上一次快照存在差异，the system shall 在报告中给出"新增/减少/不变"三态对比与净变化量。 [S-1] While 扫描目标命中硬保护名单（Roaming\Microsoft\Protect、Crypto、XP 兼容 Junction、系统组件），the system shall 强制标记为"受保护·不可处理"，且该标记不可被任何配置覆盖。 [S-2] While 判定依据仅来自启发式兜底（哈希/GUID/陈旧度），the system shall 将其置信度上限锁定为"低"，并显式提示"需人工确认"。 [X-1] If 枚举过程中遇到权限不足、路径超长（>260）、文件被占用或 reparse point，then the system shall 跳过该项、在报告中计入"未扫描/跳过"统计，并继续完成其余扫描而不中断。 [X-2] If 扫描在完成前被用户中止或异常退出，then the system shall 保留已采集的部分结果并标记为"不完整报告"，不得输出任何汇总结论性结论。 [X-3] If 版本检查请求失败或无网络，then the system shall 静默降级、不阻塞启动、不重试超过 1 次。

七、质量与防误杀

置信度模型（v0.1 用三档 + 证据清单，不做伪精确的概率值）

档位触发条件输出措辞
高多个独立证据同时成立：注册表无卸载记录 + 无匹配进程/服务 + 无自启动 + 目录陈旧（>180 天未改）+ 知识库明确标注"已停止/不存在""高度可能为残留"——仍附"删除前请确认"
中2 个证据成立，或知识库命中但缺生命周期信息（如厂商仍在但产品已下线无法判定）"疑似残留，建议核对证据"
低仅启发式兜底命中（哈希/GUID 命名、陈旧度、无 exe/无版本信息）"归属未知，需人工判断"——不做任何暗示
受保护硬保护名单命中（Microsoft 系、DPAPI、Junction、系统组件）"受保护，不可处理"——UI 上不给任何"下一步"按钮

三条不可协商的工程底线

  • 硬保护先于一切判定：保护规则在流水线最前面短路返回，不参与打分、不可被配置覆盖（EARS 的 S-1）。
  • 误判必须变成测试用例：每个真实误判（如原型首版把 Roaming\Code 判成 openaicodex 的子串误匹配）当天进回归集，形成"越用越准"的机制，而不是靠记忆。
  • 宁可漏报不可误报：召回率可以在 README 里诚实披露（"我们可能漏掉 10~20%，但不该冤枉在用的软件"），这比虚高的覆盖率更能建立信任。
