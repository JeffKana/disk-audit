# 协作契约字典

契约字典版本：1.0.0（生效日期 2026-11-15；变更依据与历史见包根 CHANGELOG.md；包根指维护源包根、发布副本根或安装根，即七个技能目录的共同父目录；CHANGELOG.md 不随单个技能目录复制；各安装副本随包同步，不得独立改版）

本文件是本包跨技能的规则维护源；技能只维护各自的操作步骤。用户明确指令、项目现行安全要求和已获授权优先；若与本包冲突，停下并记录冲突，不擅自放宽。项目采用本包时由负责人确认适配；现有项目里的权限、阈值和安全底线，不能因为安装本包而自动改变。变更共享规则需记录影响、批准人和迁移方式。

## 角色、权限与门禁

- 负责人确认范围基线、安全底线和项目约定的重大裁决，负责发布终审。PM 负责任务规划与验收判定。执行 Agent 负责被分派范围内的实现和自测。
- 本包沿用的合入分权先例：执行侧 PR 经 PM 验收通过后，由获授权的合入责任人按项目规则合入；PM 自己的 PR 交负责人把关。负责人越序合入应记录显式委托或自行把关。具体人选和操作权限以项目及用户授权为准。
- PR、远端写入、合入及发布均须有对应授权；门禁红灯不能通过删测试、跳过检查或绕过保护换绿。以当前 PR **最新 head** 对应的远端必需检查为准，本地测试不能替代；head 或基线变化后重核受影响的验收和门禁。
- 应急通道只替换故障的操作通道，不替代授权、验收、评审或 CI。仅对已验收内容，在最新基线、验收结论和必需检查均有效时合入并独立留证；条件不满足则暂停升级。发布须经授权的人工作最终确认。

## 执行边界与安全底线

1. 执行者不合入或直接推默认分支，除非用户及项目明确赋予相应职责和授权；普通工作分支推送亦遵守现有授权。
2. 不自行改变任务验收标准或安全底线；冲突和不可达条件交 PM 裁决。
3. 仅在授权目录和范围内写入；按项目安全底线保护被操作对象。
4. 新发现的问题记入执行记录，是否扩大范围由 PM 裁决。
5. 不擅自做任务范围外的修改。
6. 测试避免真实中断信号逃逸、隐式依赖 locale、全局 argv/环境泄漏；可通过替身、注入和显式参数控制。
7. 命令按环境和风险拆分；面向用户的文案按项目资源管理约定维护。
8. CI/workflow 改动须在任务范围内并获授权，走项目规定的评审流程。
9. git 推送、合入和发布遵循已确认的角色分权和实际授权。

这些边界不能替代目标项目的安全清单。涉及不可逆操作、安全敏感变更、外部副作用或计划失效时，按项目权限升级，不得以等待超时为理由绕过。

## 事实来源与文件写入者

一个制品文件只由一名已指定的责任实例写入，其他人通过自己的独立记录提供证据或建议；同一角色可有多个实例，但须指定具体实例。负责人或 PM 在分派前明确所有权；角色到实例的映射由规划 PM 在分派前显式记录执行实例与依据，并单点维护（见状态、分派与交接）。转交时先停止原写者、记录交接和版本，再由新写者接手。Git 分支隔离与合并前检查用于降低冲突，不能充当锁；发现双重认领或同一文件被并行修改时停写、保留证据并交 PM 处理，不自动择胜。

| 制品及事实 | 单一写入者 | 其他角色如何交接 |
| --- | --- | --- |
| 任务 `task.md`：范围、标准、分派与主状态 | 指定规划 PM | 执行者提出问题，验收 PM 提出状态建议；规划 PM 回填 |
| `execution.md`：所依据版本、执行、自测、未尽事项 | 已分派的执行实例 | 验收 PM 只读；转派后按记录交接 |
| `acceptance.md`：七步证据、结论、退回次数、条件项 | 指定验收 PM | 执行/故障侧提供独立证据，不能修改验收文件 |
| 独立测试证据制品（占位名 `test-report.md`，最终名称由项目治理文档确定）：被测 head、命令与退出码、结果、未覆盖项、缺陷及日志位置 | 由 independent-test 技能约束的指定独立测试实例（技能是操作规范，不改变单写者归属） | 执行实例提交被测 head 与执行记录版本；验收 PM 只读，并在 `acceptance.md` 引用其版本与位置，不得代写；轻量模式可用分别归属的 PR 评论、CI 制品等替代 |
| `merge-record.md`：合入和应急证据 | 项目指定的合入责任实例 | PM 验收记录引用其版本/位置，不替其写记录 |
| 故障记录 | 指定排障实例 | 向环境基线持有人提交事实和复现证据 |
| 产品待办、Sprint 总览、风险登记册 | 指定规划 PM | 验收和故障记录只提出更新建议 |
| 方案实测列、里程碑结论 | 指定验收 PM 或项目既有持有人 | 执行者提交可复现实证；先确认具体实例 |
| 环境基线 | 项目指定的基线持有人 | 排障实例提交事实；基线持有人确认并回填一次 |
| 代码、测试及回归用例 | 按文件分派的执行实例 | PM 确认缺陷和覆盖；实现者在其任务范围内补回归测试 |
| 决策记录 DR | 该记录的指定起草人 | 负责人按权限批准；用新记录或清晰修订历史保留变更 |

同一个人的不同角色仍须遵循权限；若项目的真实文件归属与表格不同，由负责人在任务启动时记录适配，不能把多个角色写同一个文件包装成单写者。轻量模式使用独立 PR 正文、评审记录及平台合入事件等分别归属的载体，不要求本地制品目录齐备。独立测试证据制品仅在项目委派独立测试时存在（通常为标准/高风险任务），不要求所有任务齐备；不得把测试证据并入验收文件。

## 状态、分派与交接

主线：`待执行 → 执行中 → 待验收 → 已完成`；`阻塞`、`退回`、`取消`为受控分支。规划 PM 负责状态写入；阻塞恢复必须回到阻塞前的阶段，退回修复回到执行中，取消和完成不反向改写，需要新任务时另开。禁止绕过验收直接完成。验收通过仅使任务进入 PR、必需检查与合入准备；合入须用户授权、分支保护与必需检查满足，不自动合入。`已完成`表示交付按项目要求完成且适用时已合入；有条件通过的后续项须单独登记责任人、期限和证据，不因主任务完成而消失。PR 状态、验收结论、合入情况，以及编排平台的任务派发、技能启动、输入送达与执行实例完成回执，都是独立事实，不是任务主状态。平台回执不得推进业务主状态、不得作为验收结论、不得触发合入；业务主状态仍由规划 PM 单点写入。

分派由规划 PM 在任务中记录执行实例、时间和任务版本；执行者确认后才开始。编排平台只按依赖决定任务就绪，不按角色或能力自动选择执行载体；角色到实例的映射是规划 PM 单点写入的交接字段，在任务卡或派发说明中显式指定，平台就绪状态不得改写它，不存在平台自动指派或自动切换模型/账号/供应商。可记录预计有效期或复核时间，但到期只触发 PM 检查，不自动解除分派或重派；原实例未停写、交接未确认时不可认定安全转派。无锁环境下同时出现认领必须人工仲裁。

切换执行实例按序执行：先证明原实例已停写，静默、超时或状态不可验证不构成退出证明；停留在原任务，不另开新任务规避交接；更新任务卡的 assignee 并递增 revision，contract_version 不变，范围或标准变化才递增；新实例重新确认任务版本，并回报实际读取的技能路径与契约字典版本；下游重新取证，head 变化须重测重验。

交接至少记录：上游制品位置及版本/提交、接收实例、接收时间与确认结果。执行者确认任务版本，验收者确认执行记录和待验 head，合入者确认验收结论和待合 head。交接顺序记为：分派记录（S1）、执行实例确认（S2）、执行记录首次写入（S3）；S3 不得早于 S2。执行实例在确认任务的 ACK 中一并回报其实际读取的技能路径与契约字典版本，具体记录位置由项目约定。ACK 回报的契约字典版本是共享规则文件的版本，与 `task_contract`/`contract_version` 所指的任务契约版本（任务范围与标准的版本）是两个不同事实，不得互相替代，也不得据其一推断另一；契约字典版本取自包根 CHANGELOG.md，包根指维护源包根、发布副本根或安装根，即七个技能目录的共同父目录，CHANGELOG.md 不随单个技能目录复制，各安装副本须与维护源一致。上游内容变化时，下游重新读取、确认受影响证据并留痕；不能以旧 ACK 证明新版本已被接受。版本可以是提交 SHA、PR 版本或明确递增的文档版本，不要求引入广播服务。

任务 DoR：目标、输入指针（含所依据的契约字典版本）、实现约束、可独立判定的验收标准、依赖与范围明确；标准/高风险任务还要明确责任人、风险强度和交接载体。缺失时先补齐或明确阻塞，不能让执行者猜测标准。

## 风险强度

由 PM 与负责人按项目权限选择并记录理由；不确定时先按标准处理，涉及不可逆/安全敏感/高影响变更时按高风险处理。

| 强度 | 适用示例 | 制品与检查 |
| --- | --- | --- |
| 轻量 | 范围小、可逆、依赖少的普通修复 | 可使用分别归属的任务描述、PR 正文和评审记录；保留明确标准、执行证据和接收确认 |
| 标准 | 常规跨文件或跨角色交付 | 使用任务目录中的独立任务、执行、验收与适用时合入记录 |
| 高风险 | 安全边界、不可逆、发布、重要数据或复杂依赖 | 在标准基础上记录风险、回滚与恢复验证、明确审批和独立复核 |

任何强度都保留已适用的用户授权、安全边界、可验证标准和独立验收；有 PR 时验收七步和项目必需 CI 均不免除。条件通过不能放行失败的安全底线或必需门禁。

## 验收、退回与裁决

验收结果为通过、有条件通过、退回。条件通过最多列 3 条不影响安全底线、必需门禁和本次交付核心标准的后续项，写明负责人、期限与关闭证据；不能满足这些条件就退回。验收由 PM 判定，不等同于自动获得合入授权。有独立测试证据时，测试结论取值为通过、失败或阻塞；结论为失败或阻塞的，验收判定不得覆盖测试结论，必须走退回。检查器（离线只读静态校验）的输出无论通过或失败，均不构成验收结论或合入授权。其 project 模式的适用前提是制品以任务目录文件为载体；项目治理文档选用 PR 评论、CI 制品等外部载体时，不得使用该模式做一致性判定，也不得将其对本地缺文件的报错当作流程违规，改由人工核对载体可达性与内容。退回状态或退回结论下的任务不得标记合入完成；待验收和退回状态下，验收记录对执行记录版本与 head 的引用、合入记录对验收版本与 head 的引用须与上游一致，不一致视为未确认的旧引用，不得以此推进状态或合入。检查器规则的收紧仅对新增和在飞任务生效，历史冻结卡不追溯，适用范围由项目治理文档确定。

同一卡**第 2 次退回后立即升级负责人**，由负责人决定拆卡、换方案或冻结；退回次数由验收 PM 记录。执行争议先报 PM，必要时升级负责人，材料至少包括事实、数据与可行选项及代价。48 小时未裁决时，可仅对**已获授权、可逆且不改变安全/验收底线**的事项采用事先约定的保守默认并留痕；没有此条件则继续阻塞、升级，不推定授权。里程碑 go/no-go 阈值在规划时确定，变更须按项目决策流程记录。

CI 红灯统一分为环境差异、测试质量、真实缺陷、流程/门禁配置四类；具体现象、复现和处置由 `ci-cd-ops` 维护。平台或环境故障交 `ops-runbook`，其事实由环境基线持有人登记。依赖栈须写明先后与合入顺序；同文件高风险工作先串行或拆分文件。冲突解决必须使用新鲜基线并做语义复核。

Git 树哈希相等可证明同一哈希算法下已跟踪 Git 树对象一致，不覆盖未跟踪文件、Git LFS 实际对象或子模块工作树。比对前须确认本地已测树与远端待核验提交；涉及这些外部内容时另行验证。
