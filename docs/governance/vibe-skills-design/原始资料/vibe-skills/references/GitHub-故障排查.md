# GitHub 与 Windows/MSYS 排障参考

这些是来源项目的操作经验，须按当前平台文档、项目保护规则和实际权限验证；[协作契约](契约字典.md)中的授权、当前 head 验收及 CI 边界始终适用。不要输出令牌、私钥或未脱敏的凭据。

## 区分故障

1. 比较本地分支、远端 branch tip、PR head 与检查运行的提交：若 branch 已更新、PR head 或 synchronize 检查未更新，可能是事件管道延迟；等待并交叉验证，不把缓存视为最终结果。
2. 分别探测 Git 传输、站点和 API 的可达性。SSH 失败不代表 HTTPS 或 API 也失败；只有端点与权限都可用时才考虑替代通道。代理应确认进程实际可用和注入方式，避免无效代理造成额外故障。
3. 完全不可达时记录最后可证实的远端状态，把本地提交锚定在命名分支并升级；不能用过期 main 当作最新基线完成解突。

## Git Data API 路径（仅作为已授权的替代通道）

- 先取得并核实最新目标分支、PR、仓库保护及待验收版本，明确哪些操作允许；必要时在新鲜基线上语义解突并重跑适用测试。API 可达不意味着已有合入权。
- 在目标平台确实支持且获授权时，可使用 Git Data API 创建变更 blob、以已核实的基线树创建新 tree（正确处理删除与文件模式）、以正确 parent 创建 commit，再更新允许修改的**工作分支**引用。事前核对请求目标、完整对象标识及并发变更；对非快进更新不能默认 force，受保护分支尤其不得绕过限制。
- 确认实际远端工作分支与 PR head 指向预期提交，并等待**该提交**触发并通过全部必需检查。事件未触发、检查缺失、head 改变或之前的验收不再适用时暂停；必要时重新验收，不能仅凭本地绿合入。
- 获授权的合入责任人按项目规则调用合入接口或使用常规通道，确认实际返回结果；单独记录授权、PR、基线、head、检查和最终结果。树哈希核验的覆盖范围与例外见协作契约。

## 先例排查线索

- 乱码或编码不一致：记录 shell、终端、runner 和程序各自的编码及最小复现；Python 的 UTF-8 配置只是可能的修复之一，按实际测试验证。
- Windows/MSYS 原生命令挂起：比较 ASCII 路径与环境变量，逐项检查 PATH、HOME、HOSTNAME、代理和路径转换，不先假定特定变量必然有错。
- 长命令或大 payload：可在授权范围内使用临时文件并控制敏感内容，完成后按项目要求清理；避免在日志中输出秘密。
- 文本资源冲突不能一律机械拼接，代码和测试交织冲突必须按语义复核；恢复后将可复现事实交环境基线持有人登记。
