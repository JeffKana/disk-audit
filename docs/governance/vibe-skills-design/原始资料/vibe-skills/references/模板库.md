# 项目制品模板

按[契约字典](契约字典.md)选择风险强度与写入者。以下是标准/高风险任务的示例；项目可改目录位置，但每个制品须保持独立写入者。轻量任务可用分别归属的任务描述、PR 正文、评审及平台事件代替文件。

示例中的尖括号内容需要替换。检查器只识别以下精确的 `- key: value` 头部，`yes/no` 为小写；`revision` 是文件修订号，`contract_version` 仅在任务范围/标准变化时递增，因此状态回填不会使执行 ACK 自动过期。任意可唯一定位的短字符串可作版本，提交 SHA 用于代码 head。若任务无需 PR，`merge_required: no`，并记录相应交付证据。版本有两类，不得混用：头部 `contract_version`/`task_contract` 是任务契约版本（任务范围与标准的版本）；契约字典版本是共享规则文件的版本，取自包根 CHANGELOG.md（包根指维护源包根、发布副本根或安装根，即七个技能目录的共同父目录；该文件不随单个技能目录复制）——ACK 按契约字典交接条款回报的是契约字典版本，不是任务契约版本。

## 一、任务与交接

目录示例：

```text
TASK-001/
  task.md           # 规划 PM
  execution.md      # 指定执行实例
  test-report.md    # 指定独立测试实例（independent-test 技能）写入；验收 PM 只读；未委派独立测试时省略
  acceptance.md     # 指定验收 PM
  merge-record.md   # 被指定的合入实例；无需合入时省略
```

### task.md · 规划 PM 写入

```markdown
# TASK-001 · <标题>
- type: task
- id: TASK-001
- writer: <规划 PM 实例>
- revision: <文件修订号>
- contract_version: <范围和标准的版本>
- status: 待执行
- history: 待执行
- risk: 标准
- assignee: <执行实例；未分派时写 待分派>
- merge_required: yes

## 目标与范围
<目标、包含/排除范围、输入及相关文件/决策的指针>
## 实现约束和依赖
<已知约束、安全底线指针、依赖及栈顺序>
## 验收标准
<逐项可验证标准；数据类写口径和基准>
## 分派和变更
<分派时间、执行实例、所依据 contract_version；转派或范围变更时留痕>
## 高风险补充（适用时）
<风险、审批人、回滚方案与恢复验证>
```

`history` 用 ` > ` 顺序记录主状态及受控分支，例如 `待执行 > 执行中 > 阻塞 > 执行中 > 待验收`；最后一项等于 `status`。只改状态时更新 `revision`，不改 `contract_version`。任务范围或标准改变时增加 `contract_version` 并通知下游。

### execution.md · 分派的执行实例写入

```markdown
# TASK-001 执行记录
- type: execution
- id: TASK-001
- writer: <执行实例，与 task.md 的 assignee 一致>
- version: <执行记录版本>
- task_contract: <确认的 contract_version>
- task_ack_by: <执行实例>
- task_ack_at: <确认时间>
- head: <待验代码提交 SHA；不涉及代码写 n/a>

## 完成内容
<变更及范围>
## 实现决策与依据
<决策、依赖和栈序>
## 未尽事项与风险
<无则写无；对冲突列事实、数据和选项>
## 自测证据
<命令、结果、时间、head；未执行项及原因>
```

### test-report.md · 指定独立测试实例写入（independent-test 技能；仅项目委派独立测试时）

单写者、引用与轻量替代规则见[契约字典](契约字典.md)；本模板只描述填写方式，验收 PM 只读此制品。

```markdown
# TASK-001 独立测试报告
- type: test-report
- id: TASK-001
- writer: <独立测试实例>
- version: <测试报告版本>
- task_contract: <测试所依据的 contract_version>
- execution_version: <接收的执行记录版本>
- execution_ack_by: <独立测试实例>
- execution_ack_at: <确认时间>
- head: <被测提交 SHA>
- result: <通过 / 失败 / 阻塞>

## 测试环境与前提
<环境、基线与前置条件；检查器不校验此节>
## 命令与退出码
<逐条测试的用途、退出码与时间；检查器不校验此节>
## 未覆盖项
<未覆盖范围与原因；检查器不校验此节>
## 缺陷与日志位置
<缺陷清单、日志与证据位置；检查器不校验此节>
```

头部 `execution_ack_by/at` 为测试实例对所接收执行记录的确认，检查器不校验；头部 `type/id/writer/version/task_contract/execution_version/head/result` 与 `acceptance.md` 的 `test_report_version` 引用一致性由检查器核对。

### acceptance.md · 验收 PM 写入

```markdown
# TASK-001 验收
- type: acceptance
- id: TASK-001
- writer: <验收 PM 实例>
- version: <验收记录版本>
- task_contract: <验收使用的 contract_version>
- execution_version: <接收的执行记录版本>
- execution_ack_by: <验收 PM 实例>
- execution_ack_at: <确认时间>
- head: <实际核验的提交 SHA；不涉及代码写 n/a>
- test_report_version: <引用的独立测试报告版本；未委派独立测试时省略>
- conclusion: <通过 / 有条件通过 / 退回>
- returns: <累计退回次数，非负整数>

## 七步与证据
1. 范围：<证据>
2. 项目规范：<证据>
3. 测试与回归：<证据>
4. 远端必需 CI：<当前 head 的结果；不适用时说明>
5. 每条验收标准：<逐条结论与证据>
6. 安全底线：<逐项证据；不适用时说明>
7. 结论：<理由；退回时写现象、根因、修复要求、重验口径>
## 条件项（适用时）
| 项目 | 责任人 | 期限 | 跟踪位置 | 关闭证据 |
| --- | --- | --- | --- | --- |
## 后续交接
<合入责任人、合入顺序、状态变更建议；应急留痕引用独立 merge-record>
```

### merge-record.md · 合入责任实例写入

```markdown
# TASK-001 合入记录
- type: merge
- id: TASK-001
- writer: <合入责任实例>
- version: <记录版本>
- acceptance_version: <接收的验收记录版本>
- acceptance_ack_by: <合入责任实例>
- acceptance_ack_at: <确认时间>
- head: <验收和必需检查所对应的待合提交 SHA>
- merged: yes

## 授权、门禁与结果
<授权依据、PR、当前 head 对应的必需检查、合入人/时间、合入后提交或树及证据>
## 应急通道（适用时）
<故障、采用通道、审批、基线与检查证据、终验及待办；不写入他人的验收文件>
```

### 制品存放与入库

记录 head 的制品（执行、验收、测试证据、合入记录）不得随被测 PR 提交，也不得随其被测 head 的后续变更一起提交，避免证据制品自证或随代码漂移；它们存放于任务目录或项目治理文档确定的外部载体。制品版本沿用头部 `revision`/`contract_version` 与 `version` 字段（文档版本），不以提交 SHA 充当制品版本；提交 SHA 只用于 `head`。独立测试证据的存放位置在任务目录文件（占位名 `test-report.md`）、分别归属的 PR 评论、CI 制品三者中选一，由项目治理文档确定——**需补充**：选定前不得声称该证据可复核。判据：写入者唯一且可指定、可版本化、验收方只读可达；默认值建议为任务目录文件（本包模板的默认形态）。检查器（project 模式）只核对同目录制品头部的一致性，且**仅适用于制品以任务目录文件为载体的项目**；若项目治理文档选用 PR 评论或 CI 制品作为存放载体，则不使用 project 模式做一致性判定，其可达性与内容由人工核对。此时「验收记录引用了测试证据版本但本地无同名制品文件」属于正常形态，不得据检查器输出判为流程违规。

## 二、Sprint 验收与条件项

由指定验收 PM 汇总各任务独立验收记录的链接：逐卡结论与证据、退回次数、独立抽查、合入顺序、条件项和下阶段输入。条件项跟踪至少包含事项、来源、责任人、期限、状态、关闭证据；规划 PM 据验收建议更新其持有的待办和风险登记册。汇总文件不能被其他角色直接追加。

## 三、决策记录 DR

```markdown
# DR-<序号> · <标题>
- 日期：<日期>；起草人：<单一实例>；状态：<草案/已采纳/已取代>
- 审批人：<按项目权限>
## 背景与事实
## 选项、代价与决定
## 影响、回滚与重开条件
```

## 四、治理文档骨架

项目治理：仓库、分支与权限、范围变更、安全底线、发布和归档；开发规范：测试与回归、依赖、Git/CI、AI 协作；环境基线：工具链、资源、已知限制、可复现探测与事实变更记录；决策目录：DR；敏捷资料：节奏、产品待办、里程碑口径、Sprint 计划。按项目需要增删，明确每份文档的持有人和审批权限。

## 五、故障与复盘记录

排障实例单独记录时间线、现象与影响、当前证据、故障分级、尝试与结果、最终处理、是否偏离计划/跳过门禁及授权依据、剩余风险和需回填的环境事实。敏感信息脱敏；将证据交基线持有人回填并记录 ACK。不得在未授权或门禁未满足时把故障恢复当作应急合入许可。
