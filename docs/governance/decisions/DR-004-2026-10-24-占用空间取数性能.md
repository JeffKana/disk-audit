# DR-004 · 占用空间取数的性能策略（C2 性能条件裁决）

- 日期：2026-10-24
- 状态：已采纳；**2026-10-25 修订**（见文末修订节：极小文件 MFT 驻留处理）；**2026-10-31 裁决**（见文末裁决节：三段分流边界收紧 + ②' 口径再修订 + 基准刷新复测，T2-01 ②③ 解锁）

## 背景

C2 文件枚举器为获得精确"占用空间"，对每个文件 `CreateFileW(FILE_READ_ATTRIBUTES)` + `GetFileInformationByHandleEx(FileStandardInfo)` 实查 AllocationSize（每文件 ≈30µs）。本机 AppData 合计 64 万项 → 19.36s + 5.91s ≈ 25.3s，超方案第六节"AppData ≤6s"预算 4 倍（POC 基线 4.79s 仅计逻辑大小）。正确性无争议：夹具偏差 0.000%，W0 根级文件漏算已修复。

## 决策

采用**属性分流的混合取数**策略：

1. `os.scandir` 枚举时已取得的 `entry.stat(follow_symlinks=False).st_file_attributes`（Windows）判别 `FILE_ATTRIBUTE_COMPRESSED` / `FILE_ATTRIBUTE_SPARSE_FILE`；
2. **常规文件**（未压缩、非稀疏）：占用空间 = `ceil(逻辑大小 / 簇大小) × 簇大小`（簇大小经 `GetDiskFreeSpaceW` 查询一次并缓存）。该推算对常规文件是**精确值**而非估计——NTFS 对未压缩非稀疏文件按簇对齐分配；
3. **压缩/稀疏文件**：保留逐文件开句柄实查（现机制不变）；
4. 双口径语义、汇总用占用空间的规则不变（P1）。

## 理由

压缩/稀疏文件在实际盘中占比极小（开发缓存与系统目录以常规文件为主），分流后开句柄次数下降 2~3 个数量级，预期恢复 POC 量级（≤6s）。相比"全部退回逻辑大小"（丢 P1 双口径）或"目录批查 API"（标准库不可用，需更多 ctypes 且复杂度高），该方案在零依赖约束下以最小改动保住口径精确性。

## 验收口径（Sprint 2 任务卡将引用）

1. 本机 AppData 全量恢复 ≤6s 量级（贴实测）；
2. 混合路径与纯句柄路径对同一目录的占用空间汇总一致（夹具含压缩/稀疏样本）；
3. 夹具偏差仍为 0.000%（`tools/check_size_deviation.py --fixture`）；
4. 若优化后仍 >2 倍预算 → 执行 R1 预案：按盘类型预估耗时、超 120s 建议目录级，并在选择界面披露（不砍双口径）。

## 影响面

- `disk_audit/scanner.py` 双口径取数函数重构（接口不变）；
- 测试补：压缩/稀疏属性分流用例（可用属性位 monkeypatch 模拟）；
- 若后续实测压缩盘（如启用了 NTFS 压缩的系统盘）占比异常，重开本 DR。

## 修订（2026-10-25 · PM 依据执行侧探针证据）

**被证伪的前提**：原文"常规文件簇对齐推算是精确值"不成立于 **MFT 驻留小文件**——NTFS 将约 <700~900B 的文件数据常驻 MFT 记录内，其实占为 8 字节对齐的流大小而非簇对齐。执行侧探针实证：100B 文件 `AllocationSize=104B`（非 4096B）。AppData 小文件数量庞大，纯簇对齐推算将带来 ~1% 量级**高估**，正踩 M1"偏差 <1%"边界；且原文验收口径②（混合与纯句柄**相等**）在含小文件的夹具上必然失败。

**修订后的分流规则（三段）**：

1. `st_file_attributes` 含压缩/稀疏 → 句柄实查（不变）；
2. **逻辑大小 < 簇大小 → `align8(逻辑大小)`**（8 字节向上对齐；常驻主导情形与探针 100→104 精确吻合；<簇且非常驻的文件罕见，残差 ≤ 簇大小−逻辑大小，受控）；
3. 逻辑大小 ≥ 簇大小 → 簇对齐（非常驻分配确实按簇；≥簇仍常驻的情形可忽略，常驻上限 ~900B ≪ 4096B）。

**修订后的验收口径（替换原文 §验收口径 ②）**：

- ②' 混合夹具（含 0B / ~100B / ~700B / ~1KB / ~5KB 梯度样本）上，混合路径与纯句柄路径的占用空间汇总偏差 **< 0.1%**；其中常驻小文件（<簇）逐文件 align8 规则与句柄实查一致；
- 探针（不同簇大小/NTFS 卷上 align8 vs 句柄实查）沉淀为测试或 `tools/` 测定脚本，防止环境差异回归；
- 原 ①（AppData ≤6s）、③（夹具偏差，改用上述混合夹具）、④（>2 倍预算走 R1 预案）不变，另加 **⑤ 三真实目录基准复测 <1%**（复用已登记的 `tools/baseline.json`：Programs / Tencent / Package Cache）。

**为什么不用"<簇文件句柄实查"**：AppData 小文件占比高（数以十万计），按 30µs/句柄将新增数秒，直接击穿 ≤6s 预算；align8 保持零句柄，理论残差集中于"<簇且非常驻"的稀有情形，预计总残差 ≪0.1%。

本修订不改变 DR-004 的方向（属性分流 + 推算为主、实查为辅），仅修正小文件分支与验收口径；Sprint 2 任务卡按修订版执行。

## 裁决（2026-10-31 · 负责人委托执行侧 AI 裁决，T2-01 验收②③解锁）

**背景**：修订节前提"<簇且非常驻的文件罕见，残差受控"经执行侧探针证伪（T2-01 执行记录冲突上报）——本卷（C: NTFS，簇 4096B）MFT 驻留上限实测约 600~750B 且边界不稳定（700B 样本两次探针一次驻留 704B / 一次非驻留 4096B）；713~4095B 段既 <簇又必然非驻留，align8 对每文件系统性低估 (4096−逻辑) B（仅 Programs 该段 11,906 文件、低估合计 25.9MB）；字面 ②' 梯度（含 ~700B/~1KB 非驻留样本）混合 vs 纯句柄偏差 ~23%，<0.1% 不可达成。四选项（a 维持字面 / b 边界改"≤驻留上限 align8、其余簇对齐" / c 713~4095 段恢复句柄实查 / d 其他）数据齐备待裁。

**裁决：采纳选项 c，并按探针证据收紧 align8 保留区**。分流规则（四段）：

1. 压缩/稀疏（`st_file_attributes`）→ 句柄实查（不变）；
2. **逻辑大小 ≤ 600B → align8**（600B 为本卷实测**稳定**驻留上限，≤600B 样本 align8 与句柄实查逐字节一致；712B 边界无稳定性证据，不采用）；
3. **601B ≤ 逻辑大小 < 簇大小 → 句柄实查**（驻留与否均精确；Local 该段 ~12k 文件，30µs/句柄仅增 ~0.4s，总耗 ~7s 仍在预算 2× 内，R1 不触发）；
4. 逻辑大小 ≥ 簇大小 → 簇对齐（4096B ≫ MFT 驻留上限 ~754B，必然非常驻，精确）。

全链路每段规则均有证据锚定、无推测残差，恢复"夹具偏差 0.000%"口径。

**为什么不是 a/b**：a) 维持字面实现即接受 ~0.94% 系统性低估（三段 vs 纯句柄实测 0.942%），一次吃掉 M1 ①"<1%"闸门 85% 的余量，与"占用空间精确"的项目立身标准（DR-004 开篇"正确性无争议"）冲突；b) 把"713B 以上必非常驻"当普遍规律——该论断仅有一组 704B 观测支撑，且随卷特性（MFT 记录头、文件名长度）浮动，与本次刚被证伪的"罕见"假设属同类未验证论断，风险不可控。c) 以 +0.4s 换歧义段逐文件精确，未回到"<簇全部句柄"的数秒级开销（修订节拒绝该方案的理由依然成立），方向仍是"推算为主、实查为辅"。

**②' 口径再修订**（替换修订节 ②'）：混合夹具梯度调整为 **0B / ~100B / ~600B / ~1KB / ~5KB**——剔除 ~700B（驻留不稳定窗口，属已知残差，由 `tools/probe_resident_allocation.py` 单独承载）；混合 vs 纯句柄汇总偏差 <0.1%（按本裁决实现，预期 ~0.000%）；"≤600B 样本 align8 与实查逐文件一致"保留。T2-01 卡面验收标准原文不动（红线二），认证以本节口径为准。

**① 量级判定**：**达标**。口径：与预算同数量级且 <2×（R1 不触发）——实测 Local 6.8~7.0s / Roaming 3.95~4.1s / 合计 ~11s（原 25.27s，2.3× 加速）；字面 ≤6s 未达成记为已知限制，代价即占用空间逐文件精确，本裁决有意为之。选项 c 落地后 Local 预期 ~7.4s，判定不变。
