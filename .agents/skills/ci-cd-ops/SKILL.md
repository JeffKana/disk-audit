# CI/CD 门禁管护

读取[协作契约](references/契约字典.md)中的权限、门禁和红灯分类。需要填写合入记录制品时，再按[模板库](references/模板库.md)的 merge-record.md 模板取字段。PM/负责人按项目授权维护门禁配置和规范；执行者可在明确授权的任务内实现 workflow 变更。远端保护、工作流与发布操作不得因启用技能而自动获得授权。

## 输入与输出

输入：现有 workflow、默认分支/保护规则、必需检查、运行记录、技术栈和里程碑。输出：门禁及触发矩阵、红灯诊断、保护配置或经授权评审的变更，以及面向合入责任人的证据；不改写他人验收记录。

## 工作步骤

1. 盘点现有门禁和权限，结合风险逐步建设：基础测试/环境断言，自检与构建，里程碑回归/性能，最后是发布验证。阶段及命令根据目标项目确定；新检查只有登记为必需检查后才有相应保护效果。
2. 明确 PR、默认分支、tag 和手动触发各自职责；按项目要求配置 PR-only、必需状态检查和禁止强推等保护，并记录每项失败处置。任何配置修改走项目的授权与评审流程。
3. 按契约四类诊断红灯：环境差异、测试质量、真实缺陷、流程/配置。采集失败步骤和复现证据，定位并修复根因；不要删除有效测试或跳过检查来换绿。
4. 设计可追溯发布：产物关联提交、构建和校验信息，明确人工审批及安全检查；是否保存 Release 草稿、工件形式、密钥与签名以项目实际方案为准。
5. 向PM提供独测通过所提交PR的当前head检查结论，CI通过后才进行最终验收；持续合入授权不豁免门禁、分支保护或发布确认；平台故障时交 `ops-runbook`。应急合入的权限与门禁以契约为准，本技能不提供豁免。

## 常见先例

本地与 CI 的编码/locale、环境变量和路径可能不同；测试中的真实中断信号、隐式 argv/全局状态也可能造成假绿或挂起。先核实实际 runner，再决定修环境、测试、实现或 workflow。阶段划分和工具链均需项目校准。
